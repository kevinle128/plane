## Data flow (Connect, after Q18)

1. Admin selects Connect or Retry. Plane sets `connecting`, increments `probe_generation`, stores `probe_requested_at`.
2. The Worker claims the probe only while at least 60 of the 120 answer seconds are left (`MINIMUM_PROBE_SECONDS`, `apps/api/plane/agent/services/harness_probe.py:43,96-99`). The claim returns the deadline and the seconds left.
3. Quick check: CLI found, `claude --version`, `claude auth status`, one `initialize` control request for the model list. About 2-5 s.
4. Suite lookup: the Worker reads its suite cache for (Harness, CLI version, `SUITE_VERSION`). A passing record is reused. Without one, the Worker runs the suite (the seven AD-4 checks, about 25-35 s) in the same probe, under one lock per (Harness, CLI version), and stores the record only if it passes.
5. Report version 2: the seven checks (authentication and model report from this Connect; follow-up, progress, interruption, permission and recovery from the suite record), capabilities from the suite record, models with their source, and `suite` (`suite_version`, `cli_version`, `verified_at`, `ran_now`).
6. Plane stores the report. Connected needs all seven checks, a non-empty model list and no blocking issue (rule unchanged, `harness_probe.py:141-153`).

## Key decisions

- Four `Agent` rows per workspace are created lazily on first Integrations read. The unique (workspace, harness) constraint guards `get_or_create`; an `IntegrityError` on a concurrent first read re-reads the existing row, so two reads never create two Agents or two bot users. Each Agent owns one bot `User` (`is_bot=True`, `bot_type="AGENT"`), not a `WorkspaceMember`.
- Connect/Retry sets `connecting`, increments `probe_generation` and stores `probe_requested_at`. The Worker claims the probe, runs it and posts a versioned report. A report for an older generation is rejected. A probe with no report after 120 s reads as `failed` with missing action "Worker did not answer" (derived at read time, no beat task). A Retry or Disconnect replaces a running probe: the heartbeat tells the Worker the probe is no longer current, and the Worker stops it without a report (implemented in `8bb908ac99`).
- <!-- 2026-11-14 --> Connection check (Q18, AD-4 reading accepted by the user): Connect runs the quick check; the conformance suite runs once per CLI version (data flow above). AD-4 still holds: Plane shows Connected only when a passing suite record exists for the installed version. Cache rules:
  - Key: (Harness, CLI version, `SUITE_VERSION`). `SUITE_VERSION` is a constant in the driver. A unit test pins a hash of `REQUIRED_CHECKS`, the Claude session flags and the boundary settings for fixed paths next to that constant, so a change to the checks or the boundary fails the test until the constant changes.
  - Only passing records are stored. A failed suite is not cached, so Retry always runs it again.
  - File: `<run_root>/state/conformance.json`, mode 0600, written by the Worker only. The Run root is unreadable to sandboxed commands (`claude_boundary.py:75`).
  - One lock per (Harness, CLI version) in the Worker process, so a Connect and Runs that need the same suite run it once.
  - `ensure_verified(driver, cli_version, deadline)` in `conformance.py` is the single entry point. Phase 3 calls it before each Run turn.
  - Phase 7 adds a separate Code-mode record with its own key (`CODE_SUITE_VERSION`) that stores pass and fail; it never changes the Q&A record or the Connected state. `ensure_verified` takes a `mode` argument for it; this phase implements only the Q&A mode.
  - Lost: a behavior change without a version change is found at Run time, not at Connect. The operator can delete the cache file to force the suite (Worker README).
- Q&A boundary for Claude (Q16, implemented in `apps/agent-worker/plane_agent_worker/drivers/claude_boundary.py`): the `claude` process runs without an outer OS sandbox; Bash and its child processes run in Claude Code's built-in sandbox from a Worker-written settings file (`--settings`, `--setting-sources ""`); writes are denied everywhere except Claude Code's own private temporary folder (Q16 amendment 1); reads of the Run root, the Worker token, the Plane checkout, the Claude configuration folder and credential stores are denied; an `Edit` deny rule covers the working directory; hooks are off; bypass mode is refused. The permission check needs both denials: a Write denied by the permission rule without a prompt, and a Bash write denied by the sandbox. The probe and the suite use no MCP server (`--strict-mcp-config` with no config); Runs get only the Plane MCP server from Phase 3 (Q24).
- <!-- 2026-11-14 --> Midturn input (Q19): the Claude driver reports `midturn_input=false` and does not measure it. The interruption check keeps "interrupt during a turn, then the process takes the next turn" and drops the queued-message step.
- <!-- 2026-11-14 --> Models (Q21): one `initialize` control request in a one-shot process (stdin closed after the request). If the request fails at Connect, the Worker sends the static fallback list `opus`, `sonnet`, `haiku` (CLI aliases, so the list does not age with model releases) with source `fallback`; the model report check then takes its result from the suite record. The suite itself requires a real report (its model report check fails without one). Each stored model carries `source` (`reported` or `fallback`) in the existing `reported_models` JSON, so no migration is needed. The selector labels fallback models "Not reported by Claude Code". Spec deviation: 2.1 AC 5 (epics.md:621-623) and 2.6 AC 3 (epics.md:735-737) change; user confirmation pending ([plan.md open question 6](./plan.md#open-questions-from-these-decisions)). If the user rejects the fallback, remove it and both criteria apply as written.
- Model list comes only from the report. The model selector renders only for `connected`. A selected model is copied to each new Run at creation (Phase 3), so later changes do not touch existing Runs.
- Handle: case-insensitive unique per workspace (DB constraint on `Lower(handle)` plus serializer error "An agent with this handle already exists in this workspace.").
- Save, Mentionable, Connect and Disconnect share one busy state while a request runs (prior lesson: edit-during-Save lost a draft; implemented in `5d22cc9939`). The draft keeps a baseline of server values, so a field the user did not change takes the new server value.
- Worker token: `AgentWorker` row with SHA-256 hash, created by `manage.py create_agent_worker --name mini --token-file <path>`; the command writes the token to a `0600` file and never prints it in logs. Dedicated authentication class that sets an authenticated principal; Worker views use their own `APIView` base with `throttle_classes = []` (the API-key limit of 60/min at `plane/settings/common.py:163` would block polling). <!-- red-team 2026-11-12 gitlab --> The Worker token travels in `Authorization: Bearer <token>`, never in `X-Api-Key`: `APITokenLogMiddleware` (`plane/middleware/logger.py:130-153`, registered at `plane/settings/common.py:134`) sends the request body and the response body of every `X-Api-Key` request to Celery and `APIActivityLog`, and the Phase 3 `git-credential` response body is a GitLab token. Contract test: a Worker request with the Worker token causes no `process_logs.delay` call.
- <!-- 2026-11-14 --> Worker access (Q17): no workspace allowlist and no Connect throttle. Accepted risk for review finding F2 while the instance is reachable only through Tailscale.
