# Phase 7: Code jobs and draft pull or merge request

## Goal

A member asks an existing Run to implement or fix. Plane asks for one Code-job approval. After Allow, the Run becomes a Code job with its own Worktree and Run-unique branch, waits while the Worker is at its Code-job limit, and the Harness works inside its own CLI sandbox with writes allowed only in the Worktree. Plane asks again only before push and before opening the change request. The Worker commits and pushes; Plane opens a draft change request that a human merges: a pull request on GitHub, a merge request on GitLab. All provider calls go through `GitProviderClient` ([architecture-contracts.md §11](./architecture-contracts.md#11-git-provider-boundary-and-extension-trace)); the Worker uses `git_transport.py` for clone and push. One PR, one commit per story 3.1-3.9, then G6 and G7.

## Data flow (Code job)

1. In a turn whose input is a member message, the Harness calls the Plane MCP tool `plane_request_code_job` with a short plan of the change. The tool exists only when the Harness version passed the Code-mode check (key decisions).
2. The Worker posts a permission request with action `code_job`, Run, turn and lease generation. Plane computes `branch_name` (`plane/agent/services/branch_name.py`, Phase 1) and stores the scope: Worktree path, branch, base ref, writable area (Worktree only), command network policy, sandbox kind and risk text. Plane stores `pending`, sets status `approval`, and the panel shows the Code-job card. The Q&A turn ends; the Q&A process settles under the Phase 5 rule.
3. The member selects Allow or Deny. Plane records decision, actor and time as a timeline event. Allow: `kind=code`, `code_enqueued_at=now`, and a Code turn waits for pickup. Deny: the Run stays Q&A and the next turn input tells the Harness that the Code job was denied.
4. The Worker claims a Code turn only while its running Code turns are below `PLANE_AGENT_MAX_CODE_JOBS` (Worker config, default 2). The claim sends the number of free Code places; Plane returns the oldest waiting Code turn by (`code_enqueued_at`, Run ID) that still has a valid repository grant, with `select_for_update(skip_locked=True)`. A Code turn that waits reads "Waiting for a Code slot" (derived, no slot rows).
5. On the first Code turn the Worker consumes the Code-job grant (atomic, once; Plane rechecks lease and Stop), creates the Worktree at `<run_root>/<run_id>/worktree` on `branch_name`, and records the `.git` file content. On every Code turn it runs the auth preflight (quick check), writes the Code-mode boundary for the Harness, and starts a new Harness process with CWD = Worktree (AD-6 permits a new driver session; the Run stays the same).
6. The Harness edits files and runs commands inside the Worktree. Its CLI sandbox denies writes outside the Worktree, reads of secrets and other Runs, and command network. Each tool call and each denial is a timeline event; these events are the audit of the Code job.

## Data flow (push and change request)

1. The Harness calls `plane_push` with a commit message. The Worker checks that the Worktree `.git` file still has the recorded content (else `worktree_tampered`, no git command), then commits all Worktree changes itself with `--git-dir`/`--work-tree` from Run state, `core.hooksPath=/dev/null` and `core.fsmonitor=false`. The commit is local and is not an approval point.
2. The Worker posts a `push` permission request with the commit SHA, diff summary and `branch_name` (`effect_hash` = branch, commit SHA, remote). Plane calls `GitProviderClient.is_protected_ref(repository, branch_name)` before it stores the request (no row lock during this HTTP call). A protected result stores the request as refused with `protected_ref`; the card shows the reason and offers no Allow.
3. Member Allow: the Worker calls `consume` (atomic, once). Plane checks without HTTP that `branch_name` differs from the snapshot `default_branch` and that the recorded result is not protected. GitLab only (`credential_mode=plane_token`): the Worker calls `POST runs/<id>/git-credential/` with purpose `push` and the consumed grant ID. The Worker pushes exactly the approved commit to `refs/heads/<branch_name>` with an expected-old-SHA lease through `git_transport.py`. New commits after the approval need a new push request.
4. The Harness calls `plane_open_change_request` (title, body, test summary). The Worker posts an `open_change_request` request; after Allow and consume, Plane calls `create_change_request` with source `branch_name`, target `base_ref`, title, body and `draft` from the Run policy snapshot. GitLab sets the `Draft: ` title prefix; both read the `draft` flag back and store it in `AgentRunChangeRequest`.
5. Conclusion with `mirror_conclusions=true` creates `AgentChangeRequestCommentMirror(pending)`; the Celery task posts once through `post_comment` (GitHub issue comment, GitLab merge-request note).

## Key decisions

- Escalation (3.1 AC 1): `plane_request_code_job` is available only on a turn whose input is a member message. The card, timeline and Run ID stay the same. The Worktree is created only after Allow.
- Approval model (Q22): three actions only, each with Allow and Deny: `code_job` (once per Run), `push` (each commit to publish) and `open_change_request` (once per Run). No "Allow once" versus "Allow for this Run" choice: the Code-job approval is Run-wide by nature, and push and change-request approvals each cover one named effect. A Deny of `code_job` keeps the Run in Q&A; a later member request makes a new `code_job` request.
- Code-mode boundary per Harness (replaces the Docker sandbox, AD-7 and AD-8 as changed by Q22):
  - Claude (Q16 settings builder in Code mode): Bash sandbox writes allowed only in the Worktree and in Claude Code's private temporary folder; `<worktree>/.git` write denied; `Edit` allowed in the Worktree and denied elsewhere; the same read denials as Q&A (Run root except this Run, Worker token, Plane checkout, Claude configuration folder, credential stores); command network per the network rule; hooks off; only the Plane MCP server (Q24). The exact setting keys (`sandbox.filesystem.allowWrite`, `sandbox.network`) are re-read from the installed version before coding.
  - Codex (Q23 shape, per-Run `CODEX_HOME`): `sandbox_mode = "workspace-write"`, `approval_policy = "never"`, `[sandbox_workspace_write] network_access = false`, no extra writable roots, CWD = Worktree.
  - Grok and Omp: the Q1 outer macOS profile (restored in Phase 6) in a Code variant (`sandbox/code-worktree.sb`): Worktree and the turn runtime directory writable, `.git` file and everything else read-only, network denied.
- Code-mode check: `plane_agent_worker/code/conformance_code.py` holds Code-mode assertions per driver. They are a separate cached record, not part of the Q&A suite, so a Harness version that fails a Code-mode assertion still connects for Q&A. Key: (Harness, CLI version, `CODE_SUITE_VERSION`), with its own hash pin test. Unlike the Q&A suite, the record stores pass and fail, so a failing version does not re-run the check on every request; Connect or Retry of that Agent clears a failed Code-mode record for its version. `ensure_verified(driver, cli_version, deadline, mode="code")` runs the check the first time a Code job is requested on a version, before the Worker posts the `code_job` request, and again before the first Code turn when the version changed. Assertions: (1) a write inside the Worktree succeeds; (2) a write to `<clone>/.git`, to the per-worktree gitdir and to the Worktree `.git` file is denied; (3) a write outside the Worktree is denied; (4) reads of the Worker token, another Run and the credential stores are denied; (5) command network to an outside host and to the Git provider host is denied. A Harness version with a failed Code-mode record offers no `plane_request_code_job` tool, and a request on that version tells the member "Code jobs are not available for <Harness> <version>: <check>".
- Command network (proposal, needs user confirmation): deny all network for commands in the CLI sandbox, with no allowlist. The `claude` and `codex` processes run outside their sandboxes and still reach their model hosts; this rule covers only commands the agent runs. Reasons: (a) GitHub uses `credential_mode=host`, so the Mini's own Git credentials are in reach of a `git push` run on the Mini; `denyRead` covers credential files but not the macOS keychain service, so a sandboxed `git push` to github.com could succeed if the host is reachable (`[UNVERIFIED]` whether the Claude sandbox allows the keychain lookup; check (5) makes the result irrelevant); (b) the Worktree holds private repository code, and every reachable host is a path out; (c) 3.4 starts from "no network grant" (epics.md:1405-1407), so deny-all is the spec default. Cost: no dependency install in a fresh clone. Codex has no host-level allowlist, so any later allowlist is Claude-only. The research notes that macOS Seatbelt in Codex `workspace-write` ignores `network_access` (openai/codex#10390); the direction is not clear from the note, so check (5) must prove denial on the Mini.
- Worktree and branch: `<run_root>/<run_id>/clone` gets a Worktree at `<run_root>/<run_id>/worktree` on the branch from `branch_name.py`. `branch_name` is unique in the database. `active_workspace=worktree` for every later turn. No pull or rebase while the Worktree is dirty.
- Commit ownership: the Worker commits, never the agent. Reason: a Worktree commit writes into `<clone>/.git` (objects, `worktrees/<name>`), and a sandbox that can write there can also plant `config`, hooks or a filter driver that the Worker's later git commands would run on the Host. The sandbox denies those writes, so an agent `git commit` fails; the agent instructions say that `plane_push` commits.
- Capacity (AD-11 as changed by Q22): no slot rows and no container. The Worker enforces `PLANE_AGENT_MAX_CODE_JOBS` per Worker with an in-process counter of running Code turns and asks Plane for Code work only while a place is free. Plane keeps the durable waiting order (`code_enqueued_at`, Run ID) and skips a head whose repository grant is no longer valid (carried lesson). Q&A turns never count. Stale recovery reconciles the Harness process group through `ProcessRegistry` (Phase 5) before the Run returns to pickup.
- Push and change request: push runs only in the Worker, to `refs/heads/<branch_name>` with an expected-old-SHA lease; never the default branch and never a protected branch (Plane checks `is_protected_ref` when the push request is created, compares with `default_branch` at consume, and the Worker refuses any refspec other than `refs/heads/<branch_name>`; the provider rejects a push to a protected ref server-side as a second guard, reported as `git_push_rejected`). Credentials per `credential_mode`: GitHub uses Mini-held Git credentials; GitLab uses the connection token handed out per consumed push grant over HTTPS with the connection CA bundle (architecture-contracts §11). Change-request creation goes through Plane API with `usable_token(connection)`: for GitHub this is the locked refresh function in `github_connection.py` (Phase 1; refresh tokens are single-use) <!-- red-team 2026-11-12 --> with the Q10 admin check; for GitLab it is the decrypted group token. `draft` comes from the Run policy snapshot (`AgentGitPolicy.open_as_draft` of the binding's provider). Push and change request each need their own approval (3.1 AC 12, epics.md:1335-1337).
- Recovery after a Worker crash between consume and result: the Worker compares the remote `refs/heads/<branch_name>` with the approved commit SHA and reports the push as done or failed; it never pushes again without a new request. Change-request creation happens in Plane, inside one request.
- Mirroring (3.9, G7): when `mirror_conclusions=true` and the Run has a change request, the conclusion transaction creates `AgentChangeRequestCommentMirror(pending)`; a Celery task posts once after commit. Each mirrored body carries a hidden marker with the mirror ID (`<!-- plane-agent-mirror:<id> -->`). `[UNVERIFIED]` that GitLab hides HTML comments in merge-request notes: the GitLab live check confirms it; if the marker renders, move it to a short visible footer line (`Plane Run <short_id>`) and search for that line instead. A retry after an uncertain POST calls `find_comment` with that marker before any second POST. A minute beat entry recovers missed tasks.
- GitLab token use by the Worker: the token has scope `api`, which is broader than push needs, and GitLab has no narrower per-push credential. Limits: handed out only per consumed `push` grant or per clone/fetch of a leased Run, held in memory for one git command, never given to the Harness process or a command in its sandbox (tests below).
- <!-- red-team 2026-11-12 gitlab --> Git metadata outside the sandbox's reach (kept by Q22; "container" is now "Harness sandbox"): the Worktree root is writable for the Harness, and it holds the `.git` file (`gitdir: <clone>/.git/worktrees/<name>`). If the Harness rewrites that file to point at a directory it controls, with a `config` that sets `credential.helper=!<cmd>`, `core.hooksPath`, `core.fsmonitor` or a filter driver, the Worker's next `git commit` or `git push` on the Host would run the attacker command with the GitLab token on the helper pipe or the Mini-held GitHub credentials in reach. Rules: the Code-mode boundary denies writes to the `.git` file and to `<clone>/.git`; every Worker git command on a Worktree passes `--git-dir=<clone>/.git/worktrees/<name>` and `--work-tree=<worktree>` from Run state (never discovery through the `.git` file), plus `-c core.hooksPath=/dev/null -c core.fsmonitor=false` and the Phase 3 transport options; before commit and push the Worker checks that the `.git` file content equals the value it wrote at Worktree creation, and a difference fails the effect with `worktree_tampered` and runs no git command.

### G6. Deliver a draft merge request from a Code job

- AC1: Given a Code job on a project bound to a GitLab repository and the GitLab policy "Open as draft merge request" is on, when the member has approved the Code job and then approves push and open-change-request, then the Worker commits the Worktree, pushes only `refs/heads/<branch_name>` over HTTPS with the connection token and CA bundle, and Plane creates a merge request from that branch to `base_ref` whose title starts with `Draft: `; the Run card shows "Draft merge request !<iid>" with its link. <!-- 2026-11-14 --> (Changed by Q22: commit is a Worker step, not an approval.)
- AC2: Given the draft policy is off, then the merge request is created without the prefix and shown as ready.
- AC3: Given the branch name equals the default branch or matches a protected-branch rule, then the push request is refused with `protected_ref`, the card shows the reason, and nothing is pushed.
- AC4: Given GitLab returns an error on create or the token is invalid, then the branch is kept, no merge request is claimed, and the Run shows the reason (`provider_reconnect_required` for 401).
- AC5: The Agent never merges a merge request; no Plane code path calls a merge API.
- AC6: The token never reaches the Harness process, a command in its sandbox, git argv or environment, the remote URL, `.git/config`, a Run event or a log. <!-- 2026-11-14 --> (Wording changed by Q22: no container.)

### G7. Mirror a Run conclusion to its merge request

- AC1: Given "Mirror conclusions to the merge request" is on and the Run has a merge request, when the Run concludes, then Plane posts one note with the conclusion to that merge request and stores the note ID.
- AC2: Given the note POST result is uncertain, when the task retries, then it finds the existing note by its marker and posts no second note.
- AC3: Given GitLab rejects the note, then the mirror records the failure and the work-item conclusion is unchanged.
- AC4: Given mirroring is off, then no note is posted.
