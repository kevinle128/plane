# Phase 7: Code jobs and draft pull or merge request

> **2026-11-14, decision Q27:** commands the agent runs in a Code job have network access (no deny rule, no host allowlist). Where this file proposes "deny all command network" or per-host grants, read it as Q27. Provider tokens still never reach the agent; only the Worker pushes.

> **2026-11-14, decisions Q31-Q35:** the Harness runs in a Code sandbox (Docker Sandbox), one per Code job ([architecture-contracts.md §12](./architecture-contracts.md#12-docker-sandboxes-for-runs); plan.md Docker Sandboxes open question 1). Its only writable host folder is the Worktree; the git metadata is mounted read-only; the network is open (Q27). Every "CLI sandbox", "Code-mode boundary" and "Code-mode check" rule below that only fenced the agent on the host is superseded. Effort 9.5d (was 10d).

## Goal

A member asks an existing Run to implement or fix. Plane asks for one Code-job approval. After Allow, the Run becomes a Code job with its own Worktree and Run-unique branch, waits while the Worker is at its Code-job limit, and the Harness works inside its Code sandbox, where the Worktree is the only writable host folder. Plane asks again only before push and before opening the change request. The Worker commits and pushes; Plane opens a draft change request that a human merges: a pull request on GitHub, a merge request on GitLab. All provider calls go through `GitProviderClient` ([architecture-contracts.md §11](./architecture-contracts.md#11-git-provider-boundary-and-extension-trace)); the Worker uses `git_transport.py` for clone and push. One PR, one commit per story 3.1-3.9, then G6 and G7.

## Data flow (Code job)

1. In a turn whose input is a member message, the Harness calls the Plane MCP tool `plane_request_code_job` with a short plan of the change. The tool exists when the Harness version has a passing Q&A suite record (Q31 removed the separate Code-mode check).
2. The Worker posts a permission request with action `code_job`, Run, turn and lease generation. Plane computes `branch_name` (`plane/agent/services/branch_name.py`, Phase 1) and stores the scope: Worktree path, branch, base ref, writable area (Worktree only), network policy (open, Q27), sandbox kind (Docker Sandbox, Q31) and risk text. Plane stores `pending`, sets status `approval`, and the panel shows the Code-job card. The Q&A turn ends; the Q&A process settles under the Phase 5 rule.
3. The member selects Allow or Deny. Plane records decision, actor and time as a timeline event. Allow: `kind=code`, `code_enqueued_at=now`, and a Code turn waits for pickup. Deny: the Run stays Q&A and the next turn input tells the Harness that the Code job was denied.
4. The Worker claims a Code turn only while its running Code turns are below `PLANE_AGENT_MAX_CODE_JOBS` (Worker config, default 2). The claim sends the number of free Code places; Plane returns the oldest waiting Code turn by (`code_enqueued_at`, Run ID) that still has a valid repository grant, with `select_for_update(skip_locked=True)`. A Code turn that waits reads "Waiting for a Code slot" (derived, no slot rows).
5. On the first Code turn the Worker consumes the Code-job grant (atomic, once; Plane rechecks lease and Stop), creates the Worktree at `<run_root>/code/<run_id>/worktree` on `branch_name` from the Run clone (architecture-contracts §12). On every Code turn it runs the auth preflight (quick check), creates the Code sandbox `plane-code-<run_id>` when it does not exist (§12: Worktree read-write, `<clone>/.git` and the Worktree `.git` file read-only, Code scratch folder, allow-all network), and starts a new Harness process in it through `sbx exec` with CWD = Worktree (AD-6 permits a new driver session; the Run stays the same).
6. The Harness edits files and runs commands inside the Worktree with full permissions. Host files outside the mounts do not exist in the VM; writes to the git metadata fail at the read-only mounts. Each tool call and each tool error is a timeline event; these events are the audit of the Code job.

## Data flow (push and change request)

1. The Harness calls `plane_push` with a commit message. The Worker commits all Worktree changes itself with `--git-dir`/`--work-tree` from Run state, `core.hooksPath=/dev/null` and `core.fsmonitor=false`. The commit is local and is not an approval point.
2. The Worker posts a `push` permission request with the commit SHA, diff summary and `branch_name` (`effect_hash` = branch, commit SHA, remote). Plane calls `GitProviderClient.is_protected_ref(repository, branch_name)` before it stores the request (no row lock during this HTTP call). A protected result stores the request as refused with `protected_ref`; the card shows the reason and offers no Allow.
3. Member Allow: the Worker calls `consume` (atomic, once). Plane checks without HTTP that `branch_name` differs from the snapshot `default_branch` and that the recorded result is not protected. GitLab only (`credential_mode=plane_token`): the Worker calls `POST runs/<id>/git-credential/` with purpose `push` and the consumed grant ID. The Worker pushes exactly the approved commit to `refs/heads/<branch_name>` with an expected-old-SHA lease through `git_transport.py`. New commits after the approval need a new push request.
4. The Harness calls `plane_open_change_request` (title, body, test summary). The Worker posts an `open_change_request` request; after Allow and consume, Plane calls `create_change_request` with source `branch_name`, target `base_ref`, title, body and `draft` from the Run policy snapshot. GitLab sets the `Draft: ` title prefix; both read the `draft` flag back and store it in `AgentRunChangeRequest`.
5. Conclusion with `mirror_conclusions=true` creates `AgentChangeRequestCommentMirror(pending)`; the Celery task posts once through `post_comment` (GitHub issue comment, GitLab merge-request note).

## Key decisions

- Escalation (3.1 AC 1): `plane_request_code_job` is available only on a turn whose input is a member message. The card, timeline and Run ID stay the same. The Worktree is created only after Allow.
- Approval model (Q22): three actions only, each with Allow and Deny: `code_job` (once per Run), `push` (each commit to publish) and `open_change_request` (once per Run). No "Allow once" versus "Allow for this Run" choice: the Code-job approval is Run-wide by nature, and push and change-request approvals each cover one named effect. A Deny of `code_job` keeps the Run in Q&A; a later member request makes a new `code_job` request.
- <!-- 2026-11-14 --> Code boundary (Q31, replaces the per-Harness Code-mode boundary of Q22): the Code sandbox of §12, the same for every Harness. Writable host folders: the Worktree and the Code scratch folder. Read-only: `<clone>/.git` (so the agent can run `git status`, `git diff` and `git log`) and the Worktree `.git` file (a single-file `:ro` mount). Not mounted: the Run root, the Worker token, the Plane checkout, the host Git credentials and other Runs. Network: allow all (Q27). Memory: `PLANE_AGENT_SANDBOX_MEMORY` (3.1 AC 7; no process-count limit is available).
- <!-- 2026-11-14 --> Code-mode check: removed by Q31. The Code boundary is the mount layout, which does not change with the CLI version, so no per-version Code record exists and every Harness with a passing Q&A suite offers `plane_request_code_job`. The layout is proven by native tests of `tests/test_code_sandbox.py`.
- <!-- 2026-11-14 --> Command network: open (Q27), through an allow-all rule on the Code sandbox only. Reason (a) of the earlier proposal (host Git credentials in reach of a `git push`) no longer applies: the VM has no host credentials.
- Worktree and branch: the Run clone (`<run_root>/sandboxes/<key>/clones/<run_id>/clone`, §12) gets a Worktree at `<run_root>/code/<run_id>/worktree` on the branch from `branch_name.py`. `branch_name` is unique in the database. `active_workspace=worktree` for every later turn. No pull or rebase while the Worktree is dirty.
- Commit ownership: the Worker commits, never the agent. Reason: a Worktree commit writes into `<clone>/.git` (objects, `worktrees/<name>`), and an agent that can write there can also plant `config`, hooks or a filter driver that the Worker's later git commands would run on the Host. <!-- 2026-11-14 --> `<clone>/.git` is a read-only mount in the Code sandbox (Q31), so an agent `git commit` fails; the agent instructions say that `plane_push` commits.
- Capacity (AD-11 as changed by Q22): no slot rows and no container. The Worker enforces `PLANE_AGENT_MAX_CODE_JOBS` per Worker with an in-process counter of running Code turns and asks Plane for Code work only while a place is free. Plane keeps the durable waiting order (`code_enqueued_at`, Run ID) and skips a head whose repository grant is no longer valid (carried lesson). Q&A turns never count. Stale recovery kills the in-sandbox process by its pidfile through `ProcessRegistry` (Phase 5) before the Run returns to pickup.
- Push and change request: push runs only in the Worker, to `refs/heads/<branch_name>` with an expected-old-SHA lease; never the default branch and never a protected branch (Plane checks `is_protected_ref` when the push request is created, compares with `default_branch` at consume, and the Worker refuses any refspec other than `refs/heads/<branch_name>`; the provider rejects a push to a protected ref server-side as a second guard, reported as `git_push_rejected`). Credentials per `credential_mode`: GitHub uses Mini-held Git credentials; GitLab uses the connection token handed out per consumed push grant over HTTPS with the connection CA bundle (architecture-contracts §11). Change-request creation goes through Plane API with `usable_token(connection)`: for GitHub this is the locked refresh function in `github_connection.py` (Phase 1; refresh tokens are single-use) <!-- red-team 2026-11-12 --> with the Q10 admin check; for GitLab it is the decrypted group token. `draft` comes from the Run policy snapshot (`AgentGitPolicy.open_as_draft` of the binding's provider). Push and change request each need their own approval (3.1 AC 12, epics.md:1335-1337).
- Recovery after a Worker crash between consume and result: the Worker compares the remote `refs/heads/<branch_name>` with the approved commit SHA and reports the push as done or failed; it never pushes again without a new request. Change-request creation happens in Plane, inside one request.
- Mirroring (3.9, G7): when `mirror_conclusions=true` and the Run has a change request, the conclusion transaction creates `AgentChangeRequestCommentMirror(pending)`; a Celery task posts once after commit. Each mirrored body carries a hidden marker with the mirror ID (`<!-- plane-agent-mirror:<id> -->`). `[UNVERIFIED]` that GitLab hides HTML comments in merge-request notes: the GitLab live check confirms it; if the marker renders, move it to a short visible footer line (`Plane Run <short_id>`) and search for that line instead. A retry after an uncertain POST calls `find_comment` with that marker before any second POST. A minute beat entry recovers missed tasks.
- GitLab token use by the Worker: the token has scope `api`, which is broader than push needs, and GitLab has no narrower per-push credential. Limits: handed out only per consumed `push` grant or per clone/fetch of a leased Run, held in memory for one git command, never given to the Harness process or a command in its sandbox (tests below).
- <!-- red-team 2026-11-12 gitlab --> Git metadata outside the agent's reach (changed 2026-11-14 by Q31): the agent cannot write `<clone>/.git` or the Worktree `.git` file, because both are read-only mounts in the Code sandbox. Every Worker git command on a Worktree still passes `--git-dir=<clone>/.git/worktrees/<name>` and `--work-tree=<worktree>` from Run state (never discovery through the `.git` file in the agent-writable Worktree), plus `-c core.hooksPath=/dev/null -c core.fsmonitor=false` and the Phase 3 transport options. The `.git` file content check and the `worktree_tampered` code are removed: with the read-only mount and explicit paths, the file has no effect on Worker git.

### G6. Deliver a draft merge request from a Code job

- AC1: Given a Code job on a project bound to a GitLab repository and the GitLab policy "Open as draft merge request" is on, when the member has approved the Code job and then approves push and open-change-request, then the Worker commits the Worktree, pushes only `refs/heads/<branch_name>` over HTTPS with the connection token and CA bundle, and Plane creates a merge request from that branch to `base_ref` whose title starts with `Draft: `; the Run card shows "Draft merge request !<iid>" with its link. <!-- 2026-11-14 --> (Changed by Q22: commit is a Worker step, not an approval.)
- AC2: Given the draft policy is off, then the merge request is created without the prefix and shown as ready.
- AC3: Given the branch name equals the default branch or matches a protected-branch rule, then the push request is refused with `protected_ref`, the card shows the reason, and nothing is pushed.
- AC4: Given GitLab returns an error on create or the token is invalid, then the branch is kept, no merge request is claimed, and the Run shows the reason (`provider_reconnect_required` for 401).
- AC5: The Agent never merges a merge request; no Plane code path calls a merge API.
- AC6: The token never reaches the Harness process, a command in its sandbox, git argv or environment, the remote URL, `.git/config`, a Run event or a log. <!-- 2026-11-14 --> (Wording changed by Q22: no container.)

### G7. Mirror a Run conclusion to its merge request

- AC1: Given "Mirror conclusions to the merge request" is on and the Run has a merge request, when the Run concludes, then Plane posts one note with the conclusion to that merge request and stores the note ID.
- AC2: Given the note POST result is uncertain, when the task retries, then it finds the existing note by its marker and posts no second note.
- AC3: Given GitLab rejects the note, then the mirror records the failure and the work-item conclusion is unchanged.
- AC4: Given mirroring is off, then no note is posted.
