# Phase 3: Claude Q&A Run and durable timeline

## Goal

A member mentions Claude in a work-item comment. Plane commits the comment and a Run together. The Worker clones the bound repository (GitHub or GitLab) into a fresh Run-ID CWD, runs Claude inside the Docker Sandbox of that repository with the clone mounted read-only, streams events, and posts one conclusion. The member opens a durable timeline panel. One PR, commits for 2.7 and 2.8, plus the Run-level checks deferred from 2.2-2.5. GitLab adds 1d: the Worker git transport (`git_transport.py`) with the fetch credential, the CA bundle and transport error codes.

## Data flow

1. Browser saves a comment with `<mention-component entity_name="agent_mention" entity_identifier="<agent id>">`.
2. `IssueCommentViewSet.create` (`comment.py:94`) saves the comment and its Runs inside one `transaction.atomic` block: parse agent mentions, check each Agent is connected and Mentionable, create one `AgentRun` per distinct Agent with snapshots (model, instructions, repository binding with `provider` and host, and the policy of that provider: `open_as_draft`, `mirror_conclusions`, `branch_format`), build `AgentRunContextSnapshot` v1. The existing comment permission check (`comment.py:103-118`) runs first. Both existing `.delay` calls stay after the block, as today.
3. If an Agent is not connected or not Mentionable, the whole request fails with 400 and names the Agent (no comment, no Run). Edits through `partial_update` (`comment.py:148`) never create Runs (FR8 says each new comment).
4. Worker polls `runs/claim/` (filtered by connected harness), receives lease generation and expiry, the snapshot, and the clone spec (`provider`, `clone_url`, `host`, `credential_mode`, `ca_bundle`).
5. Worker verifies remote and path, clones to `<run_root>/sandboxes/<key>/clones/<run_id>/clone` (the read-only mount of the Q&A sandbox, §12) through `git_transport.py` (GitLab: `POST runs/<id>/git-credential/` with purpose `fetch`, token on a pipe to the git credential helper, CA bundle scoped to the base URL; GitHub: Mini-held credentials), reports `clone_path` or a `git_*` failure code. <!-- 2026-11-14 --> <!-- 2026-11-14 --> Before the turn the Worker makes sure the Q&A sandbox of the key exists and is healthy (§12: create, or `sbx exec <name> true`), reads `claude --version` inside it and calls `ensure_verified` (Phase 2, Q18); on an unverified version it runs the suite first in the probe sandbox. Then it starts Claude through `sbx exec` with CWD = clone, `--dangerously-skip-permissions`, a pidfile in the Run scratch folder, the gateway values from Worker config, and `--mcp-config <scratch>/<run_id>/mcp.json` with the Plane MCP server (always) and the MCP servers listed in Worker config (Q32; Plane tools in this phase: `plane_issue_context` only).
6. Worker maps Claude events to Run events with `source_key` and posts batches with `lease_generation`. Plane assigns `seq`, rejects old generations (409) and duplicate `source_key` (returns the existing event).
7. Terminal result: Plane writes one conclusion `IssueComment` by the Agent bot user, links it to the Run, and sets `completed` or `failed`.
8. Browser polls `runs/<id>/events/?after=<seq>` every 2 s while active and reconciles by event ID. Activity shows the Run card and its conclusion; the standalone conclusion comment is not rendered twice.

## Key decisions

- Mention kind `agent_mention`: add to `TSearchEntities` (`packages/types/src/search.ts:15`), backend `SearchEndpoint` (`plane/app/views/search/base.py:334-402`), `useAdditionalEditorMention` (`apps/web/hooks/use-additional-editor-mention.tsx:51`), and the mention node renderer `apps/web/components/editor/embeds/mentions/root.tsx`. Add `disabled` and `disabledReason` to `TMentionSuggestion` (`packages/editor/src/types/mention.ts:10-17`) and honor them in `mentions-list-dropdown.tsx`.
- `process_mention` (`plane/bgtasks/email_notification_task.py:130-138`) filters `entity_name="user_mention"` so an agent ID is never looked up as a user.
- Stale is derived: `status in (in_progress, awaiting, approval)` and `lease_expires_at < now` reads as `stale` with `last_progress_at`. Lease length 5 min, renewed by heartbeat.
- Run card: one per Run, positioned by `created_at` inside `activity-comment-root.tsx`. Panel: one portal-mounted drawer opened from the full page and from peek. Escape closes the panel first, then peek (prior lesson).
- <!-- 2026-11-14 --> Q&A boundary (Q31, replaces Q16 for Runs): the Docker Sandbox microVM. Claude runs with full permissions inside it. The Run clone is under the read-only mount, so writes to it fail at the mount; host files outside the two mounts of the key do not exist in the VM (Worker token, Plane checkout, other keys, host `~/.claude`). No Claude sandbox settings, no deny rules, no hard-link probe (Q7 superseded). Spec effect: 2.7 "under an OS boundary that denies writes" (epics.md:763) reads "the clone is a read-only mount of the microVM"; the agent can still write inside the VM and in its scratch sub-folder, which never reach the clone or the host checkout.
- <!-- 2026-11-14 --> Run-time version check (Q18): before each turn the Worker compares `claude --version` with the suite cache through `ensure_verified`. A missing passing record runs the suite first, in the probe sandbox (not in the Run's sandbox), within the Run lease, and the Run shows a status event "Checking Claude Code <version>". Concurrent Runs on the same new version wait for one suite (Phase 2 lock). A failed suite fails the Run with `harness_version_unverified`, the CLI version and the failed check name in the Run result. Plane handles it in the Run result service, with no new Worker route: under a row lock, a connection in state `connected` changes to `failed` with that missing action and hint (`harness_probe.mark_version_unverified`); a connection in `connecting` (a probe in progress) is left alone. Bound: other workspaces keep reading Connected until their next Run or Connect, and each of those runs the suite at most once per version because only passing records are cached and a failed suite sets that workspace's connection to failed.
- <!-- 2026-11-14 --> Plane MCP server (Q24, transport changed by Q31): the Worker serves the Plane tools as an HTTP MCP endpoint on host loopback (`PLANE_AGENT_MCP_PORT`), reached from the VM through `host.docker.internal:<port>` with one network allow rule. The per-Run stdio server cannot run in the VM, because the VM does not have the Worker package. Each turn gets `<scratch>/<run_id>/mcp.json` with the Plane server, a random per-turn handle in its header, and the listed user servers (Q32). The handle is visible to the agent; it carries no Worker or provider token, maps to (Run, turn, lease generation) and is dropped at turn end, so a leaked handle gives only the Plane tools of that turn.
- <!-- 2026-11-14 --> Imports (Q32): Worker config `PLANE_AGENT_IMPORT_SKILLS`, `PLANE_AGENT_IMPORT_MCP_SERVERS` and `PLANE_AGENT_IMPORT_HOOKS` (comma-separated names; default empty). Skills: names under `~/.claude/skills/`, copied with `sbx cp` (sandboxes are created with `--skills=off`, see plan.md Docker Sandboxes open question 2). MCP servers: names from the user `mcpServers` in `~/.claude.json`; the Worker copies each definition into the turn's MCP config and adds a network allow rule for the host of each HTTP server; a stdio server runs inside the VM and must be installable there (README). Hooks: event names from `~/.claude/settings.json` `hooks`; the Worker writes those entries into the VM's `~/.claude/settings.json` and copies a hook script when its command is a path under `~/.claude/`. An unknown name fails the Worker start with a config error.
- <!-- 2026-11-14 --> Credentials: `PLANE_AGENT_CLAUDE_BASE_URL` and `PLANE_AGENT_CLAUDE_TOKEN_FILE` (mode 0600, outside the Run root, read like the Worker token file). The values reach `sbx exec` through its process environment or a 0600 env file, never argv (task 0 picks the path). The Worker adds the network allow rule for the base URL host and port. No host `~/.claude` is read.
- <!-- 2026-11-14 --> Sandbox lifecycle and limits: [architecture-contracts.md §12](./architecture-contracts.md#12-docker-sandboxes-for-runs) (create, health check, idle stop, least-recently-used removal at `PLANE_AGENT_MAX_SANDBOXES`, Run waits with the status event "Waiting for a sandbox" while every sandbox has an active turn, Worker renews the lease meanwhile).
- Context envelope (FR20-FR23): workspace, project, issue identifier and link, title, description, state, repository, requester, trigger comment, earlier visible comments in order with ID, author and time; member content is fenced as task data below Agent instructions; a byte budget with an exact omission count (retrieval tool arrives in Phase 4).
- Tool results split into chunks with call ID and part index; the store joins them (prior lesson).
- Provider boundary: Run creation and the Worker read only the neutral binding and clone spec (architecture-contracts §11). A missing or broken connection gives `provider_disconnected` or `provider_reconnect_required` with the `provider` field.
- Worker reachability (GitLab scope: "clear connection-failed reason when the Worker cannot reach the GitLab URL"): the Worker does not exist in Phase 1, so the first Worker contact with the provider is the clone here. `git_transport.py` maps git failures to `git_dns_failed`, `git_unreachable`, `git_tls_failed`, `git_auth_failed`, `git_not_found`. Plane stores the last result on the connection (`worker_last_error`, `worker_checked_at`; cleared on the next successful clone), the Run fails with that reason, and the provider detail page from Phase 1 shows "Worker cannot reach <host>: <reason>". No new probe type.
- The fetch credential is handed out only for a Run with a valid lease and only for `credential_mode=plane_token`. The token is never placed in argv, environment, the remote URL, `.git/config`, a file, a Run event or a log, and the Harness process never receives it. After clone the Worker sets the remote URL without credentials, so a later Harness read of `.git/config` finds no secret.
- <!-- red-team 2026-11-12 gitlab --> Git transport hardening (`git_transport.py`, every git command that the Worker runs for `credential_mode=plane_token`): `-c credential.helper=` first (an empty value resets the helper list, `gitcredentials.adoc:199-201`), then the pipe helper. Without the reset, a system helper such as `osxkeychain` also gets `get` and, after success, `store`, which writes the token into the Mini keychain. The pipe helper answers only when git's `protocol` is `https` and `host` equals the clone-spec host (with port); otherwise it returns nothing. `-c http.followRedirects=false` for both credential modes (the default is `initial`, and git then uses the redirected URL as the base for later requests, `http.adoc:370-378`). The Worker resolves the clone host itself, applies the same blocked-address rule as `plane/utils/ip_address.py:is_blocked_ip` with a Worker-config copy of `AGENT_GIT_ALLOWED_HOSTS`/`AGENT_GIT_ALLOWED_IPS`, and pins the result with `-c http.curloptResolve=<host>:<port>:<ip>` (`http.adoc:141-147`). Reason: the Plane API guard does not run on the Mini, and one Worker serves every workspace (`AgentWorker` has no workspace, architecture-contracts §3), so a workspace admin must not steer the Mini to its LAN or loopback. Also set `GIT_TERMINAL_PROMPT=0` and `-c core.askPass=`. `[UNVERIFIED]` whether git sends a credential fill for the redirect target host; the fixes above apply either way.
