## Key decisions

- One driver module per Harness under `plane_agent_worker/drivers/`. Each implements the `drivers/base.py` contract from Phases 2-5: quick check, suite, models, start/resume, send, inject (optional), interrupt, settle, permission response, shutdown, event mapping.
- <!-- 2026-11-14 --> Connection check (Q18): Connect runs the quick check (CLI found, `--version`, login status, model list). The seven AD-4 checks run as the per-version suite through `ensure_verified` (Phase 2), keyed by (Harness, CLI version, suite version of that driver). Each driver has its own `SUITE_VERSION` and hash pin test. Run turns call `ensure_verified` as in Phase 3. Spec effect: stories 2.21, 2.23 and 2.25 connect fast when the version has a passing record; their criteria are otherwise unchanged.
- Codex: app-server JSON-RPC over stdio (`codex app-server`); login status from `codex login status`; steering candidate `turn/steer`; approvals mapped to deny in Q&A.
  - <!-- 2026-11-14 --> Models (Q21): `model/list`; if it fails, `codex debug models`. Both are reports from the CLI, so 2.21 has no fallback deviation. No static list.
  - <!-- 2026-11-14 --> Runtime directory (Q20): `CODEX_HOME=<run_root>/<run_id>/codex-home`, created by the Worker for the Run (mode 0700) and kept with the Run folder, because `thread/resume` reads the thread state there. This changes Q1's "per turn, deleted after the turn" to "per Run" for Codex only; the folder goes away with the Run folder. The Worker writes `config.toml` with `sandbox_mode`, `approval_policy`, the Plane MCP server (Q24) and nothing from the user's `~/.codex/config.toml`, so user MCP servers and profiles never load.
  - <!-- 2026-11-14 --> Login: `auth.json` in the Run `CODEX_HOME` is a symbolic link to `~/.codex/auth.json`, not a copy. Reason: a ChatGPT login refreshes its tokens, and a refresh written into a copy can leave the main file with a token that the server no longer accepts. `[UNVERIFIED]` for 0.167: whether Codex follows the link on write or replaces it with a file; the suite asserts that the main file still works after a Run turn.
  - <!-- 2026-11-14 --> Q&A boundary (Q23): `sandbox_mode = "read-only"` and `approval_policy = "never"`. The `codex` process runs outside the sandbox (like `claude` under Q16); commands it starts run in Codex's sandbox. The suite's permission check must prove, on the installed version: a shell write in the clone and outside it is denied; an `apply_patch` in the clone is refused (Codex applies patches in its own process, so this is a policy check, not an OS check, and must be tested separately); reads of the Worker token, another Run folder, `~/.codex/auth.json` and the credential stores are denied. `[UNVERIFIED]` that the Codex sandbox can restrict reads at all: earlier versions allowed reads of the whole disk. Search the installed version's config schema (`sandbox_workspace_write`, readable roots) and the app-server `SandboxPolicy` type before coding. If reads cannot be restricted, Codex stays Connection failed with `read_isolation` named. Fallback option (needs the user's OK at that time, not decided here): add Q1's outer profile around `codex` for reads only.
- Grok: headless streaming JSON turns with session resume; `midturn_input=false`; Plane queue and cancel-then-next-turn; model list from `grok models`. Connected requires a proven permission pause and safe response path (2.23 AC 3); otherwise Connection failed.
- Omp: stdio RPC (`prompt`, `steer`, `follow_up`, `abort`, UI response, `get_available_models`); questions map to `AgentRunQuestion(kind=harness)` from Phase 4.
- Runtime state for Grok and Omp (Q1 accepted): a per-Run, per-turn private runtime directory under the Run root (or tmpfs), writable only for that process, deleted after the turn; clone, credentials and other Runs stay read-only under the outer macOS profile. The suite asserts writes to clone, Host, credentials and another Run fail. <!-- 2026-11-14 --> Phase 2 removed the outer profile for Claude (Q16, commit `a4b0641daa`). This phase restores `sandbox_macos.py`, `sandbox/qa-readonly.sb` and `tests/test_sandbox_macos.py` from the parent of that commit and adds the runtime-directory write rule.
- Plane tools (comments, questions) reach each Harness through MCP when the Harness supports MCP; otherwise the check fails and names it. Q24 keeps the question card, so a Harness without MCP cannot ask a structured question and is not Connected. Codex gets the Plane MCP server through its `config.toml` (`[mcp_servers]`). MCP support of Grok and Omp is `[UNVERIFIED]`; Omp UI-response maps to a question without MCP.
